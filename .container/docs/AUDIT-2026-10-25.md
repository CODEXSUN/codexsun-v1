# Deployment follow-up audit: 2026-10-25

## Scope

Review `codexsun-v1` fresh setup, retained-data setup, update, backup, rollback, and cleanup.
The user prohibited deployment, commits, and pushes. No real service was stopped, rebuilt, migrated, replaced, or cleaned.

## Findings and repairs

| Risk   | Finding                                                                                                          | Repair                                                                                                                                                   |
| ------ | ---------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------- |
| High   | Configured application storage could overlap MariaDB storage or an orphaned volume.                              | Validate actual mounts, resource names, reserved volumes, ownership, and storage drivers before mutation.                                                |
| High   | Failed Docker existence probes could skip storage backup or rollback capture.                                    | Read container and volume inventories explicitly and fail closed when either inventory is unavailable. Require a storage archive before volume deletion. |
| High   | An absent database container could cause fresh setup to reuse existing database files without explicit approval. | Require retained-volume approval and repeat the master-table check after infrastructure starts. Reuse mode skips bootstrap seeders.                      |
| High   | Cleanup archived files while application or Redis writers could still change them.                               | Stop writers gracefully, flush and stop owned Redis, verify stopped state, then archive and checksum data.                                               |
| High   | Routine updates used an online backup taken before a potentially long build.                                     | Retain that backup and take another verified backup after writers stop, immediately before migrations.                                                   |
| High   | Cleanup removed images needed by its saved rollback model.                                                       | Save and verify a compressed runtime image archive before image removal.                                                                                 |
| High   | Rollback did not verify the backup manifest, remove newly introduced services, or preserve stopped services.     | Verify every required artifact, remove added application services, recreate the old configuration, and start only previously running services.           |
| High   | Saved raw rollback credentials could be interpolated again by Compose.                                           | Escape literal dollars in raw Docker snapshots. Preserve existing escaping in rendered candidate configuration. Check real Compose configuration hashes. |
| Medium | Migration commands used mutable version tags while startup used pinned images.                                   | Use the same immutable candidate model for migration and application startup.                                                                            |
| Medium | Failure after quiescing could leave the original runtime stopped.                                                | Resume previously running survivors on backup or pre-replacement failure. Keep failure records and recovery artifacts.                                   |
| Medium | `--configure --check` could perform configuration changes.                                                       | Parse all options first and reject combined configuration mode.                                                                                          |
| Medium | Backup checks could accept a manifest that omitted the rollback file.                                            | Require exact checksum entries for every present recovery artifact. Support valid GNU text and binary checksum formats.                                  |

## Verification

The focused tests use copied source and generated data under root `dist/deployment-tests`.
A fake Docker/Git driver rejects unknown operations and records commands. It cannot invoke real Docker or Git.
The cases exercise script entry points, not only source-text assertions.

- Empty installation and migration/preflight/seed order.
- Retained database storage and skipped bootstrap seeding.
- Routine update with two backups and pinned migration images.
- Migration failure with original runtime recovery.
- Partial replacement with application rollback and removal of newly introduced Worker/Chatb services.
- Cleanup success with data and image archives while preserving the database server, volumes, and sample records.
- Dump, image-export, and inventory failure paths that prevent deletion and recover prior running services.
- A volume-inventory failure after SQL backup that cannot skip application storage protection.
- An empty master with an existing tenant database that cannot trigger bootstrap seeding through fresh or reuse mode.
- Corrupt or incomplete manifests that block rollback.
- Original stopped-service behavior and graceful shutdown without forced termination.
- Real Compose parsing for service configuration and literal credential preservation.

Run from the repository root:

```bash
node --test --test-concurrency=1 tools/deployment-env-contract.test.mjs tools/deployment-backup-safety.test.mjs tools/deployment-recovery.test.mjs tools/version-bump.test.mjs tools/sync-repository-docs.test.mjs
```

Fixture approval values follow the fixture's package version. They do not change or approve the real deployment environment.

Result: all 37 focused tests passed. Dependency layout, shell syntax, Python parsing, and Node helper syntax also passed.

## Limits

Simulated record preservation is not a MariaDB restore test or a production deployment certificate.
No real image build/load, SQL dump/restore, migration, rollback, VPS adoption, or browser acceptance test ran during this audit.
Those operations still need separate authorization and a controlled staging recovery rehearsal.
External database writers must respect the maintenance window for a consistent recovery point.
Application rollback keeps the database at its migrated state. Operators must approve backward-compatible migrations for the exact release.
Cleanup remains destructive for its declared application and owned Redis volumes after verified backup. MariaDB and its storage remain excluded.
