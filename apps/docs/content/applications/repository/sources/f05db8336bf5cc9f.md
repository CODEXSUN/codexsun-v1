## EC-D01 — Existing data and local-provider migration — RESOLVED

Evidence (live MariaDB 13.0.2, read-only inventory):
- Tenant registry `codexsun_master_db.tenants`: `CODEXSUN` → `codexsun_db` (ecommerce enabled),
  `SUKRAA` → `sukraa_db` (ecommerce disabled), `ALTEX` → `altex_db` (platform only). No tenant domains
  are registered for the local tenants.
- `codexsun_db`: 301 tables, 17 `ecommerce_*` tables, 247 `migration_schema` rows of which 31 are
  `ecommerce.modules.*`, all `applied` in batch 1 on 2026-10-22T02:14Z.
- Row counts: `ecommerce_catalog_module_data_sources` 12, `ecommerce_storefront_organisation` 1,
  `ecommerce_storefront_profiles` 1, every other `ecommerce_*` table 0. `core_products` 1,
  `core_contacts` 49, `core_companies` 1, `core_warehouses` 2, `crm_enquiries` 56.
  No imported Frappe/iShop record exists in the local tenant, so there is no imported catalog data to
  destroy — but the migration must still be safe for a deployment that does have it.
- `.env` `DEFAULT_TENANT_DB_NAME` is stale (`codexsun_local_20261011_codexsun`, which does not exist);
  Platform resolves the tenant from the registry, so this value only affects scripts that read the
  environment directly. Recorded as an environment defect, not changed by this delivery.

Alternatives: (a) leave remote-first reads and only fix the UI; (b) copy the catalog into a second
table; (c) make local projections authoritative and keep the remote path explicit.

Choice: (c). Normal catalog reads use the tenant database. The provider table
`ecommerce_catalog_module_data_sources` is retained with every existing selection intact; unset
modules read locally. Remote refresh becomes an explicit operation, never a side effect of a public
read. Existing IDs, UUIDs, SKUs, slugs, media and history are preserved; no table is dropped.

Rationale: satisfies "local Ecommerce must work without Frappe", avoids a duplicate aggregate, and
keeps the Frappe path available for the deferred EC-T17 work.

Affected contracts: EC-C01, EC-C06, EC-C09. Acceptance tests: fresh-schema and existing-schema
migration runs, repeat run, provider selections unchanged, public reads succeed with the Frappe app
disabled and with the Frappe host unreachable, no automatic remote call during a public read.
Rollback: revert the read-path change; no schema or data removal is part of it.

## EC-D02 — Stock authority — RESOLVED (no authority exists)

Evidence: 301-table scan of the tenant database for `%stock%`, `%inventory%`, `%warehouse%`,
`%reserv%`, `billing_%` finds no ledger, movement, reservation or availability table.
`core_warehouses` is a name/status/order master; `core_stock_rejection_types` is a reason master;
`core_products.opening_qty` is a `DOUBLE` opening figure. The Billing Stock Statement is a derived
company/financial-year report that ignores warehouses and cannot reserve. logicx-erp has no inventory
module. qCafe's inventory is private app-local SQLite and is not tenant data. The Ecommerce README
already documents that the browser basket does not reserve stock.

Alternatives: (a) reuse Billing's report as authority — rejected, it cannot reserve or expire;
(b) add stock to Core as a new enterprise ledger — out of scope and a second ledger risk;
(c) define a bounded Ecommerce allocation owner.

Choice: (c), as frozen in EC-C04. A new `ecommerce_inventory_allocation` ledger with
warehouse-scoped counters and atomic reservation rows (expiry, commit, release, reconciliation).
Explicit statement everywhere: this is not an enterprise stock ledger.

Affected contracts: EC-C04, EC-C03. Acceptance tests: simultaneous last-unit reservation (only one
wins), expiry releases, restart reconciliation, over-reservation rejected, unavailable reads report
unknown availability, no duplicate ledger. Rollback: drop only the new Ecommerce tables before any
accepted order references them.

## EC-D03 — Billing pricing and financial handoff — BLOCKED (owner decision)

Evidence: Billing exposes its document model over HTTP only (`POST /billing/sales`,
`/billing/sales/:id/confirm`, `/billing/receipts`, `/billing/receipts/:id/post`) with tenant JWT +
`x-company-id` + `x-financial-year-id`; no document service is exported to another package. There is
no order/checkout document, no order→invoice link, no external/idempotency reference on
`sales`/`receipts`, no credit note or refund capability, and no consumable finance event. Per-line tax
is caller-supplied; INR is enforced in code; money is `DECIMAL(18,2)` with `Math.round(x*100)/100`.

Not decided by us: who may create the invoice for an accepted order (Ecommerce on behalf of the
merchant, or staff in Billing), whether a web order may exist while invoicing is pending, and how a
refund is represented without a credit-note capability. These are business/financial-owner decisions.

Blocked consequence: EC-T08 (pricing/tax), EC-T10 (payments/Billing handoff), EC-T12 (refunds).
No fake invoice number, no local ledger and no direct Billing table write is permitted meanwhile.

## EC-D04 — Portal identity — BLOCKED (owner decision)

Evidence: `PlatformUserType` has only `super_admin | staff | tenant`; there is no customer or vendor
principal, no customer-scoped session, and no guest token. Staff permissions come from
`app_users`→`app_roles`→`app_permissions`; the storefront is unauthenticated and there is no CSRF token
(protection is a `SameSite=Strict` encrypted cookie plus an Origin/`Sec-Fetch-Site` check).

Not decided by us: whether customers and vendors become a new restricted Platform principal type
(shared across apps) or an Ecommerce-scoped session. This changes a shared security boundary, so it
needs the owner decision recorded in EC-C02 before implementation.

Blocked consequence: EC-T07, EC-T09, EC-T13. No portal route may be exposed meanwhile, and the
storefront must not imply a customer account exists.

## EC-D05 — SEO rendering — RESOLVED

Evidence: the storefront is a client-only Vite SPA with a static `index.html`, a manual
`window.location.pathname` switch, and client-side title/meta/JSON-LD mutation in `storefront.seo.ts`.
No server entry or prerender exists. A crawler therefore receives the static shell only.

Alternatives: (a) keep client-side SEO and call it complete — rejected, it fails the raw-HTML
acceptance in EC-T06; (b) build-time prerender per tenant — rejected, content is tenant-dynamic;
(c) server-rendered HTML delivered by the Ecommerce API for public document routes.

Choice: (c). Public product, collection, search, cart/checkout (noindex) and legal routes are served
complete HTML with title, description, canonical, robots, Open Graph and JSON-LD present before any
JavaScript runs, composing the same published projections the JSON API uses.

Affected contracts: EC-C09. Acceptance tests: raw HTML (no JS execution) contains the route's
canonical/title/description and 404s correctly; private routes carry `noindex`; no private cache
leakage. Not yet implemented — EC-T06 owns it; until then no SEO claim is made.

## EC-D06 — Storage/file manager — RESOLVED

Evidence: Platform supplies `publicStorageRoot` per verified tenant and a `readCompanyLogo` callback;
`StorageManagerService` is internal to Platform. Framework's `StorageAdapter` is types-only with zero
implementations. Only `storefront-organisation.storage.ts:28` writes under that Platform root. Product
and slider media resolve to `STORAGE_ROOT/ecommerce/<verified tenant key>/<kind>`
(`apps/ecommerce/api/src/env.ts:6-9,16-18`, `.env` `STORAGE_ROOT=storage/app`) via `node:fs`, so the
frozen "tenant root" rule is NOT met by today's code (EC-T00 review R1). Recorded as EC-D10/EC-T04
debt: either migrate product/slider media under the provided public root or explicitly accept the
app-level root; that decision belongs to EC-T04 and must be evidence-backed.

Choice: reuse the Platform-provided tenant root and keep validation ownership in Ecommerce media
modules. Do not clone a file manager and do not add a new shared abstraction before a second consumer
needs it. Public assets stay under `storage/<tenant>/public/ecommerce/...`; private evidence stays
under the tenant private root. No browser-supplied tenant folder or path is accepted.

Affected contracts: EC-C05. Acceptance tests: traversal/MIME/size rejection, wrong-tenant file denial,
referenced-file deletion blocked, complete uncropped images. Rollback: none needed; paths are additive.

## EC-D07 — Marketplace responsibilities — BLOCKED (owner decision)

Evidence: no vendor, commission, settlement or payout capability exists, and Billing has no payout or
refund document. Merchant-of-record, invoice issuer, tax responsibility and refund allocation are business
decisions with financial consequence.

Not decided by us: who is merchant of record for a vendor sale and who issues the invoice. Blocked
consequence: EC-T13 and EC-C10. No vendor money calculation or payout action may be implemented.

## EC-D08 — Industry baseline — RESOLVED

Choice: support physical goods with configurable variants, enquiry-only products and non-shipping
services in the local baseline. Apparel size/colour, electronics warranty/serial and dimensional
features are explicit feature flags on the product extension, not new masters. Batch/expiry,
regulated goods, bookings, subscriptions, bundles and digital fulfillment stay deferred until they
have their own domain contracts.

Affected contracts: EC-C01, EC-C04. Acceptance tests: flag combinations do not expose unsupported
purchase actions; enquiry-only and service products never enter a shipping/stock path; disabling a
feature preserves existing records. Rollback: flags are additive defaults.

## EC-D09 — Subagent host — RESOLVED

Evidence: this runtime is DeepSeek Harness with native teammates. The Lead and every teammate run the
effective model `deepseek-flash`. The requested `opencode/deepseek-v4.1-flash-free` provider/model does
not exist in this runtime; no worker claims it.
Worker capability used: three concurrent read-only inventory teammates
(`inv-core`, `inv-finance`, `inv-platform`) with one file each under `dist/ecommerce-scratch/`;
durable shared tasks `task-1..3` claimed and completed on the Team task board. Teammates do not spawn
agents.

Choice: use native subagents for independent research and for disjoint implementation leases; the
supervisor keeps shared surfaces (manifests, exports, composition, migration order, ledgers). Review is
assigned to a non-producer. Path leases are recorded in TASK.md and on the task board.

## EC-D10 — Cross-owner changes — RESOLVED (no new change authorized yet)

Recorded existing debt (not normalized, not extended):
- `catalog-data-source.repository.ts:278-316` INSERTs/UPDATEs `core_product_categories`, `core_brands`
  and `core_products` during a Frappe import. This is a cross-owner write and violates
  `assist/governance/rules.md:138`. It is reachable only from the explicit Frappe import path.
- Raw reads/joins on `core_products`/`core_brands`/`core_product_categories` in
  `product-information.repository.ts`, `storefront.repository.ts`, `catalog-matching.repository.ts`.
- `catalog-matching` outbox relay is never started; its queue job is not registered.
- Core product/category lookups exist but are not callable with a tenant database name.

Additional recorded debt (EC-T00 review R1): product and slider media are written under the app-level
`STORAGE_ROOT/ecommerce/<tenantKey>/...` path, not the Platform-provided `storage/<slug>/public` root
that the frozen rule names. EC-T04 must either migrate them or record an explicit reviewed acceptance
before claiming the media contract is met.

Decisions:
1. Local delivery creates no *new* cross-owner write and does not enable the Frappe import path.
   Making the catalog local-authoritative (EC-T02) removes the automatic remote path from public reads.
2. The two pending provider changes — a `databaseName`-based Core product/brand lookup
   (EC-C01) and a Platform `enqueue` injection for Ecommerce outbox delivery (EC-C06) — are recorded
   proposals only. Each needs its own impact review, provider tests and consumer regressions before
   any code change. They are not part of EC-T01/EC-T02.
3. No change to Core, Platform, Billing, Mail, Chat, CRM, Frappe or `packages/ui` is authorized by this
   delivery without that review. Any such change must appear here with its affected consumers and
   rollback condition before it is written.
