# Ecommerce plan

## Complete local Ecommerce delivery — 2026-10-24

The proposed [end-to-end delivery plan](E2E-PLAN.md) defines local commerce first and Frappe synchronization last.
It covers ownership, Core extensions, shared-service reuse, staff and portal UI, orders, fulfillment, returns, refunds, vendors, and tenant tests.
Its source baseline supersedes earlier assumptions about the scope of the planned Ecommerce solution.
Existing runtime capabilities and completed task evidence remain unchanged.
Cross-owner changes require a documented impact review. No shared behavior change is authorized by this plan alone.
Implementation must resolve the Phase 0 contracts before claiming transactional commerce readiness.

## Marketing integration planning — 2026-10-23

Status: design only. No runtime capability or provider access is added.
See [Marketing Phase 0](../../marketing/agent/PLAN.md#phase-0-decisions-and-contract-review), gap G09, delivery phase 6 optional.

Ecommerce retains storefront catalog extensions, promotion cards, and Campaign Events presentation.
Marketing owns acquisition Campaign. Add an optional explicit campaign UUID link without replacing Ecommerce promotion records.
Core product Brand remains Core-owned. Marketing brand/company scope does not alter catalog identity.
The browser basket does not establish checkout, order completion, or recoverable abandoned-cart events.
Require explicit consent and source contracts before any storefront marketing capture. Do not infer purchase or trigger cart recovery emails.

## Scope

Staff catalog management, matching and publishing controls, and the public storefront.

## Ownership contract

Core owns shared product identity and Frappe owns connection credentials. Public routes return published tenant content only. A browser basket does not prove order, payment, or stock-reservation support.

The root Agent Guide and governance rules remain authoritative.
Keep one root dependency installation, lockfile, and generated output tree.
Keep business roles inside their owner and compose other components through public contracts.

## Local-first read behavior (EC-T02, repaired by EC-R01/EC-R02, 2026-10-24)

Normal catalog reads are local-authoritative. A public catalog read resolves the stored per-module
provider and returns the local projection; it never calls `integrationSnapshot`, `replaceFromFrappe` or
`pullFromFrappe`. The former live Frappe window, automatic 15-minute cache refresh, and remote
fallback are removed: a stored Frappe selection alone cannot cause a public remote call.
`pullFromFrappe`/`pushToFrappe` remain available only from the authenticated Data Source actions, and
the staff Frappe item picker remains an explicit authenticated remote read.

## Current source surfaces

- `api/src/modules`: `catalog-matching`, `ecommerce-composition`, `featured-card`, `overview`, `product-image`, `product-information`, `product-variant`, `promotion-card`, `season-strip`, `storefront-announcement`, `storefront-profile`, `storefront-slider`.
- `web/src/modules`: `catalog-data-source`, `catalog-overview`, `featured-card`, `overview`, `product-image`, `product-information`, `product-variant`, `promotion-card`, `season-strip`, `storefront-profile`, `storefront-slider`.

Source presence is not release evidence. Confirm executable behavior before describing a capability as complete.

## Delivery sequence

1. Read [TASK.md](TASK.md), [SKILLS.md](SKILLS.md), and the affected public entry points.
2. Inventory the current Ecommerce implementation and its consumers.
3. Define the requested change and acceptance criteria within the scope above.
4. Resolve stored-data and public-contract compatibility before changing behavior.
5. Implement the change in its owner and update legitimate composition points.
6. Verify the owner, denied-access paths where relevant, and dependent applications.
7. Record evidence and remaining work in [TASK.md](TASK.md).
