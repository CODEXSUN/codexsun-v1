# C06 - Platform queue injection and Ecommerce transactional outbox/inbox

Status: proposed, technical impact review can proceed under existing authorization. Blocks EC-T14.

## Existing behavior

- Framework exposes event/queue types only (`packages/framework/src/events/contracts.ts`,
  `queue/contracts.ts`); there is no publisher, relay, or inbox.
- Platform owns `QueueManagerService.enqueue` and `registerQueueJobProcessor`; Mail receives an
  injected `enqueue` dependency, which is the approved composition pattern.
- Ecommerce has `ecommerce_catalog_match_outbox` and `CatalogMatchingOutboxRelay`, but the relay is
  never started and `ecommerce.catalog-match.semantic` is not registered in `queueManagerWorker.jobs`.
- `runMigrationBatch`/`rollbackMigrationBatch` and `migration_schema` are already wired for Ecommerce.

## Exact gap

Ecommerce cannot enqueue a job through Platform, so catalog matching and any later notification or
settlement job cannot run durably. The existing outbox is dead code, not a delivery guarantee.

## Proposed contract

Platform injects a narrow dependency into Ecommerce registration, matching Mail:

```ts
type EcommerceQueue = {
  enqueue(input: {
    jobKey: string;
    payload: unknown;
    idempotencyKey: string;
    tenantId: string;
    runAt?: string;
  }): Promise<{ jobId: string; deduplicated: boolean }>;
};
```

Platform registers the Ecommerce job keys and processors in the same composition step. The payload is
validated with Zod at the processor boundary; tenant identity and module activation are reloaded there,
never trusted from the payload.

Ecommerce owns these additive tenant-local tables:

```sql
ecommerce_outbox (
  id INT NOT NULL AUTO_INCREMENT PRIMARY KEY,
  uuid CHAR(8) NOT NULL DEFAULT (LOWER(SUBSTRING(MD5(UUID()),1,8))) UNIQUE,
  tenant_uuid CHAR(8) NOT NULL,
  aggregate_type VARCHAR(60) NOT NULL,
  aggregate_uuid CHAR(8) NOT NULL,
  event_type VARCHAR(80) NOT NULL,
  payload_json JSON NOT NULL,
  status VARCHAR(24) NOT NULL DEFAULT 'pending', -- pending | dispatched | failed | dead_letter
  attempts INT NOT NULL DEFAULT 0,
  next_attempt_at DATETIME NOT NULL,
  dispatched_at DATETIME NULL,
  created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  updated_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  UNIQUE KEY ecommerce_outbox_event_unique (aggregate_type, aggregate_uuid, event_type),
  KEY ecommerce_outbox_ready (status, next_attempt_at)
) CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;

ecommerce_inbox (
  id INT NOT NULL AUTO_INCREMENT PRIMARY KEY,
  uuid CHAR(8) NOT NULL DEFAULT (LOWER(SUBSTRING(MD5(UUID()),1,8))) UNIQUE,
  tenant_uuid CHAR(8) NOT NULL,
  consumer_key VARCHAR(80) NOT NULL,
  message_uuid CHAR(8) NOT NULL,
  received_at DATETIME NOT NULL,
  processed_at DATETIME NULL,
  result_json JSON NULL,
  UNIQUE KEY ecommerce_inbox_message_unique (tenant_uuid, consumer_key, message_uuid)
) CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;
```

- `uuid`, `aggregate_uuid`, and `message_uuid` are the repository's eight-lowercase-hex public record
  identifiers (`CHAR(8)`), not `CHAR(36)` UUIDs.
- `tenant_uuid CHAR(8)` is the validated tenant identity carried in the background envelope for
  Platform enqueue and consumer verification. It is not a row-level tenant selector; the tenant
  database remains the isolation boundary.
- Statuses are `VARCHAR(24)` domain values validated at the processor boundary; no MySQL `ENUM`.
- The domain transaction writes the business row and the outbox row together. A single relay claims
  pending rows with a lease, calls `enqueue`, and marks `dispatched`; a crash after enqueue is safe
  because `(tenant, jobKey, idempotencyKey)` is deduplicated by the queue. Consumers insert the inbox row
  before side effects, reject an envelope tenant UUID that does not match the bound tenant, and treat a
  duplicate as a no-op.

Retry policy: exponential backoff with jitter, a bounded attempt count, and a dead-letter state that
requires staff action. Do not delete failed rows. Do not retry validation errors.

## Consumers and tests

Consumers: catalog match, order confirmation mail intent, payment reconciliation polling, settlement
reports. Tests: one domain transaction produces exactly one outbox row; duplicate enqueue returns the
same job; relay crash after enqueue does not duplicate; consumer replay is a no-op; tenant mismatch is
rejected; job key without a registered processor fails closed; existing Mail queue tests remain green.

## Repository identity conformance

- Primary keys: `id INT NOT NULL AUTO_INCREMENT`, matching Ecommerce `ecommerce_*` tables; no `BIGINT`.
- Public identifiers: `CHAR(8)` lowercase hex, matching Ecommerce record UUIDs and `tenants.uuid`.
- Statuses: `VARCHAR(24)` values validated in code; no MySQL `ENUM`.
- Envelope exception: the tenant registry key is `tenants.id INT`, but the already-established queue and
  session envelope carries the tenant public UUID as a string (`queue_jobs.tenant_id VARCHAR(80)`,
  `auth_sessions.tenant_id VARCHAR(64)`, and the `tenantId` claim). The outbox/inbox therefore store
  `tenant_uuid CHAR(8)` to enqueue and verify that envelope; they do not add an integer tenant FK to
  tenant-local business rows.
- Job payloads validate tenant identity and module activation at the processor boundary; a payload
  claim is never authority.

## Owner decision still required

None of the technical shape above requires a new business policy. Platform owner must confirm the
injection shape, job-key namespace, payload size limit, and whether the queue deduplication window is
long enough for the outbox retry window. If it is not, Ecommerce keeps an `enqueued_at` marker and
skips re-enqueue after the window; the inbox still makes consumption safe.
