# Core

### External customer identity

`resolveExternalContactForDatabase` creates or resolves an active Customer or Supplier through a source-scoped external key.
For Frappe imports, the local contact code is the actual remote document name (for example, `C9138`); the Frappe app stores the site-scoped source identity separately. Legacy `EXT-<hash>` customer codes are corrected in place on a verified re-import, preserving the contact ID and related records.
The resolver appends mobile numbers and never merges contacts by phone alone. The owning transaction locks the contact while attaching phones, and concurrent creation retries are bounded.
Existing email, address, bank, and social rows are preserved. Frappe document codes cannot be edited through Contact update. Frappe owns source identity construction and import links.

### Contact duplicate protection

Core rejects a repeated customer name and phone combination within the same contact group.
Contacts without a group share the ungrouped scope. Name case and repeated whitespace do not distinguish contacts.
Phone punctuation does not distinguish numbers. The check covers all stored phone rows and the primary phone.
Create, edit, and external phone attachment check within the save transaction.
A locked tenant contact-type reference row serializes these saves to prevent concurrent duplicates without a schema change.
Different names or groups may share a phone. Soft-deleted records do not block reuse.
Existing duplicates remain unchanged. A conflicting save returns HTTP 409 with a clear message.
Distinct external source identities that collide locally are rejected rather than merged.

The public `contactIdsForEmailPolicy` lookup returns every matching recipient identity ID, including inactive/deleted identities.
It reads only Core-owned email fields. CRM consumes these IDs to check restrictions without merging contacts.
Platform selects the trusted tenant database before calling the contract. No new public HTTP search or write permission is added.

### Existing company favicon schema

`core.organisation.company-favicon-v2` adds the nullable `favicon_path` column to existing tenant company tables.
A separate versioned step is required because applied company baseline migrations are skipped.
This prevents company updates from failing on older schemas. Existing company values remain unchanged.

## Safe unit defaults and upgrades

The tracked `core.common.products.units.defaults-v2` step runs after standard Core column upgrades.
Fresh tables reserve ID 1 for the hyphen unit, then add `pcs`, `nos`, and the existing measurement defaults.
Existing tables keep every occupied ID, unit name, lifecycle state, and reference.
An existing `Nos` row satisfies `nos` through normalized name matching. The upgrade does not rename it or merge aliases.
If ID 1 already belongs to another unit, hyphen receives a new ID. Existing IDs are never swapped.
The unit list displays hyphen first even when its legacy ID or sort order differs.
Repeated migrations and seeds add only missing unit names and preserve existing unit rows.

Product creation and null-unit seed backfills resolve the active hyphen by name, rather than preferring Nos or assuming ID 1.
Explicit product units and existing non-null product/document units remain unchanged.
An existing placeholder product with a conflicting unit still requires a reviewed correction. Seeding does not overwrite it.
The hyphen unit cannot be renamed, deactivated, or deleted through UnitsService.

## Company placeholder provenance

New owner seeds carry a seed_placeholder marker atomically with creation.
Separate tracked company/default-setting migrations add the marker without changing applied baseline checksums.
The legacy company upgrade recognizes only the complete unchanged known seed signature and migration-created metadata.
Customized companies are not adopted. Default settings are adopted only while they retain the original seed selection and metadata.
Normal company/settings changes clear the marker. Data Bridge uses Core's public seed signature, not numeric ID guesses.
A verified single-source company may replace the placeholder's business values while keeping its identity and references.
Confirmed business matches clear unused seed status so another source cannot repurpose the company later.

Standard users receive Core view/create access. Core records do not have a draft lifecycle, so their edits/deletion remain administrator-only.
