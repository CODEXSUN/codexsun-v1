# Data Migration

Super Admin DevKit for visual, audited transfers from a saved external MariaDB source to a registered active CODEXSUN tenant MariaDB database. Platform owns authentication, destination tenant lookup, and destination database secret resolution. This DevKit owns encrypted external source connections, previews, table copying, and the `data_migration_runs` master ledger.

Database Settings, Migration Mapper, Transfer Review, Migration Audit, Migration Queue, and Migration Analysis are under the first Super Admin side-menu group, Data sync, in that order. Opening Data Migration from Super Admin Apps goes directly to Migration Mapper. Database Settings has no in-page Migration Mapper shortcut; use the Data sync menu. The current Platform server preset is shown as a compact action beside Add server connection. Editing a saved connection omits the form heading and description. A Super Admin can save multiple MariaDB server connections in Database Settings. These credentials are used only by Data Migration and Migration Analysis, and do not alter CODEXSUN runtime database settings. Database is optional. A server connection can be tested and saved without selecting a database, then databases accessible to that account can be fetched and selected later. The connection is tested and saved before the page fetches its accessible databases. The database list hides MariaDB system databases and the configured Platform master database. A Super Admin selects a database and saves the source again before starting a migration. An edited connection can keep its stored password by leaving the password field blank. Migration Analysis compares source tables with one registered destination tenant.

Migration Mapper creates a named migration session. The API generates its UUID. The session stores references to the saved external source and destination tenant, source and target database name snapshots, and an optional source tenant reference. Each table pair is a child row with source/target table names, saved source/target row counts, mapping status, and migration status. Each field pair is a child row with source/destination field, status, and the actual Super Admin actor. Table and field rows use internal IDs and foreign keys; tenant IDs are validated against the Platform registry. Table Mapping lists saved table pairs with Review/Edit actions so mappings can be reopened. Transfer Review is also available as a separate Data sync menu page and opens a saved migration session for plan review. Select a table to review its fields, select a field to edit its destination, and run compatibility analysis before starting the migration. The table data viewer is read only and loads only when Show data is selected; Refresh reloads it. It shows all columns and up to 100 rows per independently paginated source and destination side. Use the Columns menu to select multiple mapped field pairs and filter both sides to those columns; Show all restores every source and destination column. Compare visible data checks only the currently shown source and destination rows against the selected mapped fields and marks matches in both previews. Hide matches and Hide unmatched filter the visible sample rows. Row checkboxes add source or destination samples to a selected-rows banner below the previews; selections can be individually removed or cleared. The comparison, filters, and selection are read only, do not inspect rows outside the loaded pages, and do not write to either database. Redacted or binary values are never treated as matches. Sensitive fields are redacted in the viewer. Compatibility analysis separately counts full-row exact matches across mapped fields and source rows that collide with a mapped destination unique key but have different values. Existing destination rows block insert-only migration; matching rows are not merged, overwritten, or skipped. Save a mapping for every source table in the session before running it. Batch preflight checks database snapshots, mapped values, row counts, row limits, target emptiness, storage engines, and dependency order before writing. Source and destination tables must use InnoDB. The batch copies in source foreign-key dependency order inside one destination transaction; a failed insert rolls back the entire batch. Each table receives a run-history entry. Source access uses consistent-snapshot reads only; the migration never writes to the source. Each table is limited to 10,000 rows. Tables must already exist at the destination; the tool does not apply schema migrations. External passwords are encrypted with an application secret before storage in the Platform master database; they never return to the browser.

Before a batch run, Generate query plan builds and persists a server-side, read-only plan containing quoted SELECT/INSERT templates, mapped columns, row counts, and keyed fingerprints of source data and schemas. The plan contains no row values or credentials. Resolve every blocker, review the SQL templates, and finalize the plan; execution is rejected unless the server recomputes the same fingerprint and plan hash. Mapping changes mark the plan stale. Run history records the actual operator and per-table copied row counts. The query preview is informational; the API executes its own parameterized inserts. Current row checkboxes remain sample-only and do not restrict batch rows.

Hand off places selected saved row samples for one mapped table pair into the Migration Audit queue; it does not require mapping every source table. The queue list shows summary rows. Opening an item loads a separate detail page with the raw SQL template and a read-only table of its persisted sample data. The API builds a SQL dump from the saved field mapping and row selection, with a snapshot hash, source/target database names, operator, and queue/review timestamps. SQL remains parameterized and does not contain row values, credentials, or browser-provided SQL. Sample positions are review context, not stable record identifiers, so the dump is not executable migration input. Migration Audit can mark the review complete. Migration Queue lists reviewed audit items and runs the associated session only when its complete server-generated plan is finalized; it executes the full mapped session, not only the selected audit samples. The API rechecks the finalized plan, schemas, data fingerprints, and destination safety before writing.

The query builder can save selected read-only source samples under a query-batch master and row-child schema. The master references the saved source connection and snapshots its host, database, and user; the source password remains encrypted in the connection record and is never duplicated into query-batch data. Child rows store selected sample row numbers, redacted JSON previews, field-value choices, and status. Missing target fields offer database-default, custom, or referenced foreign-key choices based on destination schema metadata. Saving these sample rows does not change the existing all-mapped-tables batch migration behavior. Treat the saved row JSON as a UI review sample, not authoritative source evidence: the save endpoint currently accepts preview JSON from the browser and does not re-read the source row at save time.

Only Migration Queue exposes a public migration execution action. A queue item must be reviewed and its session plan must be finalized before execution. Migration Analysis is read-only; Transfer Review prepares mappings, samples, and plans. The former direct single-table and saved-plan execution endpoints have been removed. The master `data_migration_plans` table remains in the schema for existing-database compatibility, but is no longer an active API or UI workflow.

At field mapping, source fields can be included or excluded from the transfer. Excluded fields are listed in the generated plan and are not copied. Required destination fields still need a mapping or a destination default/generated value. ID, UUID, created_by, and created_at are optional when the destination schema allows them to be omitted; there are no special name-based exceptions.

Database Settings offers searchable choices from saved source names, hosts, databases, users, and ports. Port choices also include 3306 and 3307. Each choice has a Create option for a new value. Choosing a saved source name fills its public connection details. After a connection is saved, the Database choice also shows databases returned by that connection. The password is never suggested or filled.

Database Settings also offers the current Platform MariaDB server as a source preset. The server returns only its host, port, and user for display. When selected, the API tests the connection and stores its password encrypted; the password is never sent to the browser. The source starts without a selected database, and the configured Platform master database remains excluded from database discovery and migration.

External source connections require verified TLS by default. Super Admin can explicitly choose Disabled for a source that does not support TLS. The destination uses the registered CODEXSUN tenant connection policy.
The encrypted source password depends on the Platform `JWT_SECRET`; preserve that secret or re-encrypt saved source connections during key rotation. A saved source can be verified or disabled without removing its run history. Remove erases the saved password and deactivates the connection while retaining migration run history.

This is a bounded, one-way batch-copy workflow, not ongoing bidirectional sync. The source is a saved external MariaDB connection; the destination is a registered tenant database. Existing destination rows block batch execution; the tool does not overwrite or merge them. The tool rejects source and destination connections that resolve to the same host, port, and database. This feature does not copy the Platform master database.

## Verification

Production web proxies must preserve `/api/data-migration` and `/api/data-bridge` when forwarding to Platform.
These APIs already include `/api` in their server routes. Do not strip it or send these requests to the SPA fallback.
The CODEXSUN, Billing, and demo Nginx templates include these routes.
Changing the repository templates requires a later web-image rebuild and deployment to affect a VPS.
The frontend reports non-JSON responses, unavailable gateways, and malformed JSON without exposing response bodies.
Normal API errors retain their request IDs.

`migration.services.test.ts` covers source lookup, authenticated context, mutations, and response diagnostics.
`tools/e2e/data-migration-proxy.e2e.ts` exercises real local Nginx against all three web templates.
Set `CODEXSUN_TEST_NGINX_BINARY` to an available Nginx executable before running it with `node --import tsx --test`.
The proxy test is explicitly skipped when that executable is unavailable.
It uses local disposable ports and files and never contacts a VPS or writes business records.

From the repository root run `npm run typecheck -w @codexsun/data-migration-api`, `npm run typecheck -w @codexsun/data-migration-web`, `npm run lint -w @codexsun/data-migration-api`, `npm run lint -w @codexsun/data-migration-web`, and the Platform API/web checks. Verify fresh and existing master migration, a real two-database transfer, denied access, rollback, and browser navigation before production use.

`npm run test:e2e:data-migration` uses configured local MariaDB credentials to create three uniquely named disposable schemas. It checks the tracked source and ledger migration, encrypted source setup, preview, copy, repeat-copy rejection, failed-insert rollback, and denied API access, then removes those schemas.
