# Platform plan

## Marketing integration planning — 2026-10-23

Status: design only. No runtime capability or provider access is added.
See [Marketing Phase 0](../../marketing/agent/PLAN.md#phase-0-decisions-and-contract-review), gap G07, delivery phase 1.

Compose Marketing activation, Plan Access/entitlement, permissions, navigation, migrations, queue processors, and infrastructure contracts.
Marketing owns Campaign, Consent, Capture, connector business lifecycle, and business validation.
Add only minimal server-owned provider account claims/callback routing metadata. Keep tokens and business content in tenant databases.
Validate tenant registry state for HTTP, OAuth callbacks, webhook routing, jobs, files, exports, and live updates.
Use revocable tenant automation principals with bounded grants. Browser logout must not transfer authority or bypass revocation.
Review existing CRM/Frappe activation coupling. Marketing must not depend on Frappe as a source or bypass current activation checks.
Optional app loss stops that integration while preserving submissions and unrelated Marketing capabilities.
Keep cross-client management outside tenant Marketing. Future support access requires a separate owner and audited scope.

## Future staged deployment and traffic routing

Status: architecture decision only. Do not change the current production runtime until a separately approved rollout.

Keep Platform as a composed modular-monolith API. Do not create independent CRM, Billing, Core, or Devkit production APIs merely because their source folders are separate.

Cloudflare Tunnel remains the public edge. It maps public application and verified tenant-domain hostnames to one internal router service on the Docker network. Do not change public DNS, public ports, or the Tunnel hostname route during a normal release. Preserve the incoming Host header so Platform can resolve the verified tenant domain.

Add Traefik as the future internal Docker router. It selects the active application slot and routes web, API, Shop, and WebSocket traffic to that slot. Keep Nginx inside the existing Web and Shop containers for static-file delivery and app-local proxy behavior.

Use a separate staging server, Cloudflare Tunnel, router, databases, Redis state, media paths, credentials, and external-provider sandbox settings. Staging must not send customer mail, messages, payments, compliance submissions, or integration updates.

Production uses Blue and Green composed slots. Deploy the tested immutable image digest to the inactive slot, check health and tenant-domain behavior, then change only the Traefik upstream. Keep the previous slot available for rollback. Database migrations must use expand-contract compatibility. Application rollback does not reverse an applied database migration.

Both slots may share the production Platform and tenant databases, Redis, and media only during the short switch window. Run one active queue worker while two application slots exist. Do not let Blue and Green process the same queue concurrently.

Split workers, schedulers, reporting, integrations, compliance processing, or other proven heavy workloads before splitting CRM or Billing APIs. Split an application into its own runtime only after measured scale, reliability, security, compliance, or independent team-release pressure justifies its added operational cost.

## Scope

The authenticated runtime, tenant routing, application composition, entitlements, permissions, queues, storage, administration, and Windows host.

## Ownership contract

Composition registers public app contracts. Business CRUD stays in each owner. Preserve Corporate ID resolution, signed session context, live authorization, and server-only secrets.

The root Agent Guide and governance rules remain authoritative.
Keep one root dependency installation, lockfile, and generated output tree.
Keep business roles inside their owner and compose other components through public contracts.

## Delivery sequence

1. For focused work, read the affected source and direct public entry points.
2. Use the full inventory and acceptance process only for new capability, tenancy, permission, data, or cross-module work.
3. Implement the change in its owner and update legitimate composition points.
4. Run the smallest relevant verification for the changed behavior.
5. Update TASK only when the user requests documentation, or when scope, contracts, operations, or release evidence changes.

## TConnect buyer composition
