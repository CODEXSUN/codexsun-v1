# Data Bridge

Data Bridge is a Super Admin DevKit for reviewed, queued business-data migration between verified database connections.
Platform owns authentication, active tenant resolution, navigation composition, and queue dispatch.
Data Migration owns external source credentials. Data Bridge uses its public server-side resolver.

## Pages and stages

The sidebar contains Database Connection, Common Tables, Master Tables, Billing Tables, and Report.
Each business group contains Table Mapping, Field Mapping, Import Preparation, Confirm Import, and Results tabs.
The tabs share a persisted session and connection pair. Saved mappings and legacy links remain accessible.

Common Tables owns the common-parent policy. Master Tables owns master and child scope.
Billing Tables discovers installed business tables and excludes runtime history and command queues.
Each group owns its API policy/service/routes and frontend client/workspace in matching module folders.
Technical transfer, snapshot, report, connection, and transport concerns remain in their respective owners.

## Import behavior

Use a dedicated source account with only `SELECT` and, when needed, `SHOW VIEW` grants.
Data Bridge rejects writable, administrative, grantable, and role grants. It opens the source session in read-only mode.
The connection guard covers previews, mapped transfers, common and business imports, reports, and tenant user copies.
The guard checks the connected schema names and uses a target advisory lock to detect aliases of the same server and schema.
This check does not prove that separate servers, proxies, Galera nodes, replicas, or shared storage are independent.
Before a real import, verify the full routing and replication topology and use separate source and target storage.
The database guard does not protect source media storage. Verify media source access and routing separately.
The local-clients E2E requires `CODEXSUN_BRIDGE_SOURCE_USER` and `CODEXSUN_BRIDGE_SOURCE_PASSWORD` for an existing read-only account.
It does not create or change source database grants. Its target and report databases must be disposable.

Inspect live tables, fields, indexes, defaults, and relationships before mapping.
Support different table and field names through explicit mapping.
Select stable source records and business fields. Resolve source parents through target business identity.
Do not assume equal numeric keys identify the same record across databases.
Prepare target values and audit existing data before confirmation.
Queue approved writes with trusted target context, revisions, locks, schema checks, and transactions.
Preserve existing target conflicts as warnings. Use the separate explicit correction contract for approved updates.

Normal transfers use saved source snapshots and recheck schema and destination values during execution.
Reprepare when source, parents, mappings, or routing change. Correction plans apply stronger fingerprint checks.
Current imports commit per table. Verify complete invoice aggregates after all related tables finish.
There is no single cross-table invoice transaction. Guided transfers require explicit child selection.
Private snapshots and backups never belong in Git.

The worker runs Common → Masters → Billing in parent order and verifies invoice children afterward.

## Company reuse and tenant user transfer

Company preparation counts the source rows and checks the destination business identity first.
An exact destination company match takes precedence over an unused seed.
For a single-company source, Data Bridge can update one verified untouched owner seed in place.
Core owns the seed marker and its pristine signature. Normal company/settings edits clear the marker.
Ambiguous companies, multiple unmatched source companies, and customized targets produce warnings instead of another company.
Preparation is read-only. Execution checks the saved target snapshot, source values, source count, and seed eligibility again.
Company IDs, UUIDs, creation metadata, and existing references remain unchanged.
Default-company settings resolve the source company and financial year to target identities before updating their seed row.
Confirmed exact seed matches become claimed business identities and cannot be reused for a different source later.
Reports distinguish seed updates from inserted rows. Legacy review paths block duplicate companies and direct unresolved mappings to the guided flow.

Ordered business import also calls Platform's dedicated tenant-user transfer contract.
Platform rechecks the active Super Admin, registered target, supported password format, and active target User role.
New users retain their exact supported PBKDF2 hash. Existing target accounts, passwords, and roles remain unchanged.
Source administrator privileges, protected flags, role definitions, and source permission grants are not copied.
Core/Billing/CRM own their standard User access defaults. App activation and tenant visibility boundaries still apply.
Unsupported hashes, duplicate usernames, missing roles, and unsupported account schemas produce warnings without password resets.
User outcomes have a separate paginated Users tab and appear in Warnings. Hashes never enter report JSON, SQL previews, or queue payloads.

## Automatic company branding

Company transfers also copy configured light/dark logos and favicons after the target company commits.
Branding paths are excluded from business identity comparison. Existing different target images are preserved.
Platform requires a trusted read-only source-media mapping in CODEXSUN_DATA_BRIDGE_MEDIA_SOURCES.
Missing or unsafe files produce report warnings. Copy results are persisted on each company transfer row.

## User readiness and preserved navigation

Account transfer requires verified company data and an active mapped default company and financial year.
If the only remaining singleton difference is landing_app, retain the target navigation choice as a warning.
Verify the completed transfer session belongs to the exact source and target pair.
Require one active singleton, translated positive company/year IDs, source-mode identity fields, and matching remaining mapped values.
Changed source data, ambiguous settings, cross-tenant sessions, or other differences keep user copying blocked.
Platform still rechecks active Super Admin authority and active target context before copying supported credentials and User-role grants.
