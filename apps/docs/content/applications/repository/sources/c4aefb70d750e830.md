# cxmobile working rules

## Apply this guidance

Read the root agent instructions and Assist Fast Work Default first.
For architecture work, read this app's README, PLAN, TASK, and AUDIT.
This file contains repository guidance. It grants no runtime permission or deployment authority.

## Scope and ownership

- cxmobile is the React + Capacitor CODEXSUN client for Android and iPhone.
- Keep the client in `apps/cxmobile/client` when implementation starts.
- cxmobile owns the mobile host, shell, native adapters, app composition, and distribution evidence.
- Platform owns authentication, sessions, tenant routing, permission infrastructure, and app activation.
- CRM, Billing, Chat, and Ecommerce keep all business modules and their fixed services.
- Core keeps shared contact, product, category, brand, company, and financial-year records.
- Reuse public package exports. Add explicit public contracts rather than importing private sibling files.
- Keep responsive business changes in their existing module. Keep reusable controls in `@codexsun/ui`.
- Do not create a generic business CRUD engine or duplicate owner screens under cxmobile.
- Do not create a cxmobile business API or a second authoritative database.
- Use one React root, router, query client, transport, and session coordinator per running client.
- Keep navigation metadata separate from entity schemas, fixed business paths, and CRUD behavior.
- Load only approved owner routes. Do not import the full Platform desk to obtain a mobile shell.

## Native and session rules

- Package reviewed local assets. Release builds must not load an arbitrary remote application.
- Resolve API origins through reviewed configuration. Never accept arbitrary origins from links or notifications.
- Preserve server-owned tenant routing, Corporate ID rules, host binding, active sessions, and live permissions.
- Complete PLAN phase M1 on both platforms before general screen integration.
- Keep session secrets in native-protected storage and out of JavaScript, logs, URLs, and plain files.
- Never expose HttpOnly cookies through bridge results or response headers.
- Do not weaken browser origin enforcement or cookie attributes for a native workaround.
- Keep native transport separate from business resource paths and authorization decisions.
- Close sockets, cancel requests, and clear scoped data on logout, expiry, or account changes.
- Validate notification and deep-link destinations against typed owner routes and current server permissions.
- Treat biometrics as a local unlock. They never grant a server permission.
- Initialize reviewed runtime configuration before importing owner services that read configuration at module load.
- Do not depend on the browser global fetch interceptor as native authentication infrastructure.
- Bind requests, query caches, files, and sockets to environment, session, tenant, user, company, and year.
- Reject late results after context changes and close old subscriptions before activating the next context.

## Business and device rules

- Preserve company/year/currency scope and financial lifecycle behavior in Billing.
- Preserve CRM record visibility and existing integration policy. Tasks remain local.
- Preserve Chat membership, read cursors, attachment checks, and realtime authorization.
- Preserve published-only storefront access and isolation between staff and customer contexts.
- Do not describe a local basket as checkout, paid orders, or stock reservation.
- Polling does not establish operating-system push delivery or background execution.
- Native feature availability requires platform-specific proof and useful denied-permission behavior.
- Offline drafts require owner-defined persistence, retry identities, conflicts, encryption, and cleanup.
- Never replay posting, settlement, approval, or destructive actions through a generic offline queue.

## Repository and verification rules

- Use npm from the repository root. Preserve its single lockfile and root dependency installation.
- Keep build outputs and caches under root `dist`. Track reviewed native source, not native build caches.
- Do not generate placeholder modules, dummy adapters, empty source folders, or scripts that claim unimplemented operations.
- Keep client version metadata aligned with the root version source.
- Keep signing keys, provisioning material, local SDK paths, and provider credentials outside source control.
- Preserve unrelated working-tree changes and existing Flutter clients.
- Track exact feature coverage in TASK before claiming complete four-app support.
- Report documentation, browser, API/database, Android, iOS, signing, distribution, and publication evidence separately.
- A mock, successful typecheck, or installed shell does not prove a persisted mobile workflow.
- Do not mark an unchecked acceptance entry complete without its required evidence.
- Keep measured budgets and first integrated slice acceptance in PLAN aligned with TASK.
- Record source-only, hidden, API-only, and new backend features explicitly rather than assuming route-key parity.
- Preserve backward-compatible APIs for supported installed clients and keep release build numbers monotonic.
- Keep AUDIT findings open until runtime evidence resolves their implementation requirements.
