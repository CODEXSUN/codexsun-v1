## Component documentation

### Customer import source

Customer import uses LogicX `Mobile Contact Customer`, not the person-level Frappe `Contact` DocType.
Each preview row is one mobile/customer association. Standalone `Mobile Contact` rows without a customer association are not business customers.
On import, validate the linked `Mobile Contact` and active `Customer`, then use the current Customer name and ten-digit mobile.

- One remote Customer maps to one local Core customer, even when it has several mobiles.
- Different remote Customers remain separate when they share a mobile or display name.
- The Core contact code is the actual Frappe Customer document name (for example, `C9138`). A separate `frappe_contact_customer_identity` row scopes the source identity by Frappe site, so equal document names from different sites cannot silently merge.
- Previously imported `EXT-<hash>` customer codes are corrected in place on re-import, preserving the local contact ID and related records. Conflicting IDs or cross-site links are shown as mismatches and blocked for review.
- Import links use a `mobile-customer:` namespace in `frappe_contact_imports`. Existing person Contact imports remain unchanged.
- Imported mobile numbers append to Core phone rows. Existing emails, addresses, phones, and other customer details are preserved.
- The selected-import endpoints remain `/frappe/contacts/remote` and `/frappe/contacts/pull`.
  Preview now identifies `source: mobile-contact-customer`, includes `customerId`, and returns `email: null` because the source has no email field.
- Tenant permission checks, verified connection access, and the import-complete lock remain in force. Import actions produce Platform audit events.

Core remains the local identity owner. This source change does not make CRM screens read customer data directly from Frappe.
Migration `1.0.87` adds the site-scoped customer identity table. Existing generated codes are converted only when the matching Frappe customer association is imported again. Frappe import and export views show matched, new, or mismatch identity status.
Contact export requires an exact existing Frappe Customer/Supplier ID. If its 10-digit mobile number has no `Mobile Contact`, export creates one with only `{ mobile_number }`; it does not create another Customer or Supplier, and a mismatch remains blocked.

### Sync direction contract

Live sync defaults to **Frappe → CRM only** after migration `frappe.connection.inbound-checkpoint-v9`.
Select **Both directions (enquiries and contact mobiles)** to allow automatic exports.
Inbound mode also pauses the CRM enquiry outbox relay and previously queued automatic enquiry exports.
Pending outbox events remain stored. Explicit manual exports remain separate, permission-protected operations.
Enquiry exports send the assignee through the verified, site-scoped Employee mapping.
Unmapped or ambiguous assignees block export. An unmapped remote Employee blocks import
without clearing the saved CRM allocation. Explicit remote unassignment still clears allocation.
Group and status-details exports remain deferred. An absent remote group preserves the list
on CRM-originated enquiries.

Status exports use the installed Enquiry Status names before considering supported legacy aliases.
They do not send `Pending` when the site supports `Open` instead.

Frappe assigns the enquiry number during creation. CRM adopts the returned `Q<number>` or
`ENQ<number>` serial after linking, rather than predicting the next remote counter value.
Reconciliation uses a transaction, temporary serials for swaps, and an activity entry for each change.
Record IDs, links, comments, and timestamps remain intact. Local records occupying a remote serial
move to an unused CRM serial. Conflicting Q/ENQ serials block reconciliation for review.

Failed enquiry and comment events can be retried through the authorized queue API only while
bidirectional enquiry sync and the verified connection are enabled. Unsupported event types stay blocked.

Enable the verified connection, queue worker, Live sync, and Enquiries. Select the interval, starting at one minute.
The scheduler checks every ten seconds. The interval controls when a pass becomes due;
network failures, retries, and a running history import can delay completion.
CRM enquiry saves dispatch their durable outbox immediately, in order, including opening comments.
The scheduled importer also updates linked CRM-originated enquiries in bidirectional mode.
Unsent local enquiry changes block reverse updates. Local source identity, creator, email,
and date precision remain preserved.

With Contacts enabled in bidirectional mode, CRM contact saves queue the existing mobile-only
export contract. An exact existing Customer or Supplier ID is required. This does not create
Customer, Supplier, or Mobile Contact Customer associations.
Migration `crm.frappe-sync.dispatch-revision-v2` separates new edits from earlier retry jobs.
Migration `frappe.connection.contact-export-start-v10` starts recovery from activation time;
it does not automatically export historical contacts.
New errors remain visible during retries on contacts, enquiries, duties, and duty reports.
These web views refresh status every second. Tasks remain local and show **Not configured**.
Duty and SOP delivery retains its separate approved outbound contract.
Run `npm exec -- tsx --test tools/e2e/frappe-contact-export-queue.e2e.ts` for immediate database
queue delivery, first-error persistence, lost-response recovery, and duplicate prevention.
The first scheduled import reads all enquiry history. Later runs use the last successful checkpoint with a one-day overlap.
The queue captures its checkpoint before reading Frappe. Only a complete successful pass advances that checkpoint.
Any failed row or comment keeps the checkpoint unchanged and retries through the queue.
Old jobs cannot move the checkpoint backward. A connection change cannot reuse another site's checkpoint.
Existing cross-site enquiry links block a site switch for identity review.
No Frappe hook is required. This flow polls Frappe and does not provide instant webhook delivery.
The Live sync queue provides **Import all enquiry history** in inbound mode.

Imports read complete Enquiry documents and all returned Job Comments fields.
Versioned local source records retain company, address, Mobile Contact Customer, status details, unknown fields, and comment metadata.
CRM enquiry details expose these read-only records under **Frappe sync**, with paged source history.
Record visibility checks also protect this source endpoint.
Mapped fields remain normal CRM fields. Additional source fields do not become editable CRM fields automatically.
Source file URLs remain references. This flow does not copy remote file binaries or import unrelated DocTypes.

Blank source status defaults to New. Blank priority defaults to Normal.
Missing due date, group, and assignee stay empty. Unknown statuses and invalid dates fail clearly.
CRM-only captured email survives source updates. Newer local enquiry edits block automatic overwrites for review.
Exact Q/ENQ names remain distinct when their numeric serials collide. CRM assigns a free local number when needed.
Imported comment edits update the same local row. Replies retain parent links, and source revisions preserve earlier content.
Imported comment retry keys include the local enquiry identity. On refresh, legacy rows retain
their row IDs and move to the scoped key. Existing legacy duplicates remain preserved; replies
prefer the scoped parent. Author changes and source IDs reused under another enquiry cannot
collide with the global comment retry index.
Per-database import locks serialize selected and queued imports.

Run `npm run test:e2e:frappe-inbound-queue` for disposable database and queue verification.
Remote responses are controlled in this suite. It covers partial failure, retry, checkpoints, fields, replies, and concurrent import denial.
On 2026-10-23, authenticated live reads as Vijay confirmed Q930, installed Enquiry fields, and the Job Comments wildcard read API.
That live check made no remote writes. Production migration, continuous scheduling, Redis delivery, and browser acceptance remain separate checks.

Enquiry creation, its opening comment, and later comments/replies enter the durable CRM outbox
before queue delivery. The approved comment worker creates standalone `Job Comments` with reply
links. Frappe v2 accepts explicit document names: CODEXSUN derives one from the site and persisted
outbox retry key, preventing duplicate inserts after lost responses or competing deliveries.
Inbound sync skips locally posted comments, and imported comments do not emit outbound events.
This approval does not enable general Activities exports.

The opt-in `tools/e2e/frappe-enquiries-live.e2e.ts` verifies authenticated Vijay enquiry POST,
persisted database queue delivery, Customer linking, opening comment, parent comment, reply,
web/mobile request retries, and recovery after a Job Comments response is lost. Set
`CODEXSUN_FRAPPE_LIVE_ENQUIRY_WRITE=1` only for an approved live run. It retains marked fixtures
and queue history, and consumes only its own jobs through the database queue service.

Before a new outbound Enquiry is created, CODEXSUN resolves its ten-digit number to a Frappe
`Mobile Contact`. If absent, it creates only `{ mobile_number }`, then reads the exact identity
back. A lost response or concurrent duplicate is recovered by looking up the unique number again.
Each retry looks up the contact before creating it. This minimal contact creation is explicitly
approved as part of enquiry export; it does not enable standalone Contact exports.
The ten-digit number is the Frappe `Mobile Contact` link identity. When a local contact has no
Customer identity for the connected site, enquiry export sends only `mobile`. It leaves `customer`
and `mobile_customer` empty and retains the local Customer fields. It does not invent a Customer.
A mapped Customer still requires its exact Mobile Contact Customer association. Multiple Customer
identities or a missing mapped association block export. The legacy no-local-contact lookup still
requires one unique association. Minimal Mobile Contact creation retains lookup-before-create and
lost-response recovery behavior.

Frappe-to-CRM imports copy selected Frappe records into local tenant databases. Mobile customers,
enquiries, activities, and call logs use direct selected-row imports. Enquiry and call-log bulk imports
use background jobs. Enquiry live sync polls Frappe changes incrementally and updates linked local
enquiries and comments while preserving Frappe creation, modified, and comment timestamps. CRM remains
the write interface for local operations; imported records remain linked to their Frappe identity.

Enquiry imports accept both `ENQ<number>` and `Q<number>` document names and preserve the numeric
serial. The exact remote document name remains the link identity, so `ENQ27` and `Q930` are saved
and queried using their respective source names. Imports also preserve Frappe creation and modified
timestamps, mapped creator and assignee, the current Customer display name and mobile, and
Comment/Info timeline entries.
Enquiry timeline rows use the standalone LogicX `Job Comments` DocType, filtered by `job_type =
Enquiry` and `job_id = <remote enquiry name>`. Reads use `/api/v2/method/frappe.client.get_list`;
approved exports create or update `/api/v2/document/Job Comments` records. The LogicX DocType grants
TM User read/create/write and TM Admin read/create/write/delete at permission level 0. The former
`Enquiry Message` child table is copied by the LogicX `migrate_enquiry_messages_to_job_comments`
patch, so CODEXSUN no longer reads or writes that legacy table at runtime.
Remote enquiry titles are converted from Quill/HTML to plain text before preview and local persistence;
the rich `Enquiry Details` field is preserved so formatting and embedded images remain available.
The enquiry's read-only `user_employee` field is the business creator shown in CRM; it maps through
the verified Employee-to-local-user mapping. Frappe's document `owner` is a fallback when that
Employee has no unique local mapping. `assigned_to_employee` is authoritative: clearing it clears
the local allocation, and an ambiguous or unmapped Employee is never substituted with a stale user.
The identity audit flags one Employee code mapped to multiple local users.
Imported comments retain their source timestamps and mapped author, and their retry key is scoped to
the Frappe comment identity. A saved verified connection must be able to read Enquiry, Customer, and
Comment resources. If any source record cannot be read or mapped, that row is reported as failed and
must be resolved before declaring the import complete.

CRM-to-Frappe has separate controls. The Live Sync page may verify contacts, enquiries, activities,
and call logs, but outbound export is restricted to enquiries at the Frappe service boundary for
both manual requests and queued jobs. Contacts, activities, and call logs remain blocked until their
outbound scope is approved. Imports are unchanged. CRM also has an approved automatic outbox for SOP
items, duty assignments, and duty reports.

The connection API reports whether the connection is usable and whether background workers are
enabled. Queued imports and exports reject new jobs when workers are disabled. Direct selected-row
imports do not require a background worker.

### Identity audit

The Frappe Identity audit page automatically compares each saved user mapping with the connected Frappe `User` and
`Employee` records. It reports local account state, Frappe account state and email, employee code,
employee user ID and status, stale site mappings, duplicate employee matches, and unmapped local
users. The audit is read-only and runs deterministic field checks in the Frappe API. It does not
create, edit, or remove either local or Frappe users. The audit remains available after the initial
Frappe import is locked, provided the Frappe connection is verified and the viewer has
`frappe.connection.manage`.

Frappe-imported comments and call logs resolve the remote owner through the saved identity mapping.
When no mapping exists, the original Frappe owner is retained as the actor. Import-generated initial
enquiry activity rows display the mapped enquiry creator; later synchronization updates remain
attributed to the sync service.

Use the public verified connection contract. Resolve tenant credentials server-side. Queue retryable transfers and preserve parent mapping, idempotency, and audit behavior.

## Tenant sync activation

The Live sync switch also controls CRM integration visibility and manual CRM transfer requests.
The public `FrappeLiveSyncService.access()` reads only persisted tenant connection and live-sync settings.
An enabled saved connection and the master switch enable visibility.
Verified connection, bidirectional mode, and an unpaused schedule additionally enable outbound work.
Platform checks CRM and Frappe app activation before reading integration settings.
Turning the switch off preserves source links, local records, checkpoints, and pending change events.
Queued jobs recheck access before remote work. A request already in flight can finish.
Connection setup and connection verification do not require live sync.

## Server availability and queue holds

Open **Frappe > Server availability** at `/app/frappe/availability`.
The tenant can enable daily server hours, choose an IANA timezone, and set opening and closing times.
Defaults are 08:00 to 21:00 in Asia/Kolkata. The hours switch starts off for existing tenants.
This setting controls sync access. It does not start or stop the Frappe server.

Migration `frappe.connection.availability-v11` adds `frappe_availability_settings` without changing business records or source links.
Apply the tracked Frappe migration before enabling workers on an existing installation.
GET/PUT `/frappe/availability` and POST `/frappe/availability/check` require the tenant Frappe app and `frappe.connection.manage`.
The connection check uses authenticated, read-only `/api/method/ping` with a five-second timeout.
Checks share a persisted lease. Online results last one minute. Unavailable results wait five minutes before another probe.
Outside server hours, no probe or automatic sync job is sent. Pending work waits until the next opening.
A late server start keeps work held until a successful probe. Successful import checkpoints remain unchanged during a hold.
Existing direction, master switch, module switches, permissions, and stable retry identities remain in force.

Queue Manager records held jobs as pending with a waiting label, reason, and next check time.
A hold does not consume queue attempts. BullMQ moves the same delivery to delayed without recording a failed attempt.
Transport failures after a successful check open the circuit. Mapping and validation failures retain their normal error handling.
Local CRM remains usable during holds. Existing failed history is preserved.

Run `npx tsx --test apps/frappe/api/src/modules/live-sync/live-sync.availability.policy.test.ts apps/frappe/api/src/modules/live-sync/live-sync.availability.routes.test.ts tools/e2e/frappe-availability.e2e.ts`.
The local clone audit report is generated under root `dist/local-cloud`. Do not commit its credentials or database backups.
