# C02 - Restricted customer/vendor principal and membership (Platform -> portals)

Status: proposed, owner decision required. Blocks EC-T07, EC-T09, EC-T13.

## Existing behavior

- `PlatformUserType = "super_admin" | "staff" | "tenant"` (`packages/framework/src/api/tenant-access.ts`).
- Sessions are tenant staff sessions: encrypted `HttpOnly`, `SameSite=Strict` cookie plus
  `x-codexsun-session-slot`, with an Origin/`Sec-Fetch-Site` check. There is no CSRF token.
- `access_users` and `app_users` are staff/admin surfaces. `/storefront/*` is unauthenticated.
- A browser-supplied `x-tenant-id`/`x-tenant-db` never authenticates; Platform replaces it from the
  trusted session.
- There is no guest token, customer principal, vendor principal, membership table, or scoped portal
  session.

## Exact gap

Ecommerce cannot identify a storefront customer or a marketplace vendor, so it cannot scope orders,
addresses, wishlists, returns, offers, or settlement to a person or company. Building a parallel login
inside Ecommerce would duplicate Platform identity and bypass tenant membership.

## Proposed contract (smallest compatible change)

Add the portal identity inside each tenant database. The principal references tenant-local Core
records, and buyer/vendor data must not be copied into the master Platform database.

```sql
app_portal_principals (
  id                INT NOT NULL AUTO_INCREMENT PRIMARY KEY,
  uuid              CHAR(8) NOT NULL DEFAULT (LOWER(SUBSTRING(MD5(UUID()),1,8))) UNIQUE,
  principal_type    VARCHAR(24) NOT NULL, -- customer | vendor
  core_contact_id   INT NULL,
  email             VARCHAR(191) NOT NULL,
  status            VARCHAR(24) NOT NULL DEFAULT 'invited', -- invited | active | suspended | revoked
  email_verified_at DATETIME NULL,
  created_at        DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  updated_at        DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  UNIQUE KEY app_portal_principals_email (principal_type, email),
  UNIQUE KEY app_portal_principals_contact (principal_type, core_contact_id),
  INDEX app_portal_principals_status (status),
  CONSTRAINT app_portal_principals_contact_fk FOREIGN KEY (core_contact_id)
    REFERENCES core_contacts (id) ON DELETE RESTRICT
) CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;

app_portal_memberships (
  id           INT NOT NULL AUTO_INCREMENT PRIMARY KEY,
  uuid         CHAR(8) NOT NULL DEFAULT (LOWER(SUBSTRING(MD5(UUID()),1,8))) UNIQUE,
  principal_id INT NOT NULL,
  company_id   INT NULL,
  role         VARCHAR(24) NOT NULL, -- customer | vendor_admin | vendor_staff
  status       VARCHAR(24) NOT NULL DEFAULT 'active', -- active | revoked
  created_at   DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  updated_at   DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  UNIQUE KEY app_portal_memberships_role (principal_id, company_id, role),
  INDEX app_portal_memberships_company (company_id, role, status),
  CONSTRAINT app_portal_memberships_principal_fk FOREIGN KEY (principal_id)
    REFERENCES app_portal_principals (id) ON DELETE CASCADE,
  CONSTRAINT app_portal_memberships_company_fk FOREIGN KEY (company_id)
    REFERENCES core_companies (id) ON DELETE RESTRICT
) CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;
```

- `uuid` is the repository's eight-lowercase-hex public identifier, not a `CHAR(36)` UUID.
- Status and type values are `VARCHAR(24/32)` domain values validated by the service, not MySQL `ENUM`.
- There is no `tenant_id` column: the selected tenant database is the isolation boundary. The master
  Platform database must not copy Core contacts, companies, addresses, or portal profile rows.
- Both tables reference Core rows in the same tenant database and never write Core tables.
- Migration ordering: these FK-bearing tables must run after `core_contacts` and `core_companies`.
  The current `tenantRuntimeMigrations` batch runs before Core in tenant provisioning, so Platform must
  register this addition in a post-Core tenant step. If that ordering cannot be changed, omit only the
  two Core foreign keys, keep the `INT` references, enforce them in the Platform service, and record
  that exception explicitly. Default to FK enforcement.
- MariaDB/MySQL unique keys treat a `NULL` `company_id` as distinct. If company-less memberships must
  be unique, add a stored generated `company_key INT AS (COALESCE(company_id, 0))` and the unique key
  over `(principal_id, company_key, role)`, or enforce the same rule in the service.

Session claims add `userType = 'portal'` (additive to `PlatformUserType`), `principalType`,
`principalUuid` (the `app_portal_principals.uuid` `CHAR(8)` value), `contactId` (Core `INT` id),
`companyId` (Core `INT` id), and `membershipRole`. The existing `tenantId` claim remains the tenant
`CHAR(8)` UUID string already used by tenant sessions. JWT claims are strings; they map to the
`CHAR(8)` and `INT` columns above. Portal routes are separate prefixes (`/portal/customer/*`,
`/portal/vendor/*`) and use a distinct cookie name and JWT audience (`codexsun-portal`) so a staff
session cannot be replayed as a portal session. Platform remains the only issuer/verifier of the
session. Ecommerce consumes `getPortalPrincipal(request)` from the Platform contract; it never reads
the cookie or membership tables directly.

Permissions are membership-scoped, not global: `ecommerce.portal.customer.orders.view`,
`ecommerce.portal.customer.profile.manage`, `ecommerce.portal.vendor.offers.manage`,
`ecommerce.portal.vendor.settlement.view`. A customer may never receive vendor permissions.

## Authorization and scope

- Staff authentication is unchanged: `super_admin`/`staff` sessions, cookies, `requireTenantAccess`,
  and existing staff routes keep current behavior. Portal routes accept only `userType = 'portal'` with
  the portal audience; staff routes continue to reject portal sessions.
- A portal principal is tenant-local and record-local. Every query runs against the session's
  validated tenant database, and a customer may act only on records linked to its `core_contact_id` or
  membership `company_id`; a vendor may act only for its membership `company_id`.
- Portal claims never grant tenant-wide or global permissions, and no portal route may accept a
  browser-supplied tenant, company, contact, or principal selector as authority.
- The master Platform store keeps only the tenant registry, staff/super-admin credentials, and the
  session snapshot. This proposal adds no global customer/vendor identity. Portal principals are
  tenant-local rows bound to Core contact/company `INT` ids in the same tenant database. If a
  cross-tenant portal account is later required, the master binding uses
  `tenant_id INT` -> `tenants.id` plus `principal_uuid CHAR(8)`; it must not store `core_contact_id`
  or `company_id`.

## Abuse cases and required denials

- Staff session calling a portal route -> 403; portal session calling staff routes -> 403.
- Principal from tenant A with host/session tenant B -> 404/403, no record existence leak.
- Customer reading another customer's order/address/wishlist by UUID -> 404, not 403 with data.
- Vendor reading another vendor's offers/suborders/settlements -> 404.
- Revoked or suspended membership -> 401/403 on the next request, even with a valid cookie.
- Cross-site POST without the Platform Origin check -> rejected; email change/re-invite requires
  re-verification.
- Duplicate email within the same `principal_type` is rejected by the unique key; duplicate membership
  is idempotent. Reusing one email for both a customer and a vendor principal is not implicit and needs
  an explicit owner decision.

## Backward compatibility

- No change to staff login, the existing `staff`/`super_admin`/`tenant` values of `PlatformUserType`,
  staff cookies, staff route guards, or current `/storefront/*` reads. `portal` is additive.
- Existing public storefront remains unauthenticated. Guest checkout, if later approved, uses a
  separate short-lived guest token and never gains portal permissions.
- Core contact/company rows remain Core-owned; Platform stores only the binding and membership.

## Repository identity conformance

- IDs: `INT NOT NULL AUTO_INCREMENT` for primary keys and Core references, matching
  `core_contacts.id`, `core_companies.id`, and `app_users.id`. There is no `BIGINT`.
- Public identifiers: proposed `CHAR(8)` lowercase hex, matching the eight-hex values in
  `tenants.uuid`, `app_users.uuid`, `core_contacts.uuid`, `core_companies.uuid`, and Ecommerce record
  UUIDs. Platform creates `tenants.uuid` and `app_users.uuid` as `VARCHAR(8)` and the framework
  normalizes them in place to `CHAR(8)`; the proposed tenant-local portal columns use `CHAR(8)` from
  the start and store the same eight-lowercase-hex values.
- Lifecycle: `VARCHAR(24)` values validated by the service; no MySQL `ENUM`.
- Tenancy: the tenant database is the boundary, so these tenant-local tables add no `tenant_id`. The
  master registry key remains `tenants.id INT AUTO_INCREMENT`; its `tenants.uuid` is created
  `VARCHAR(8)` and normalized to `CHAR(8)`.
- Session exception: the existing `tenantId` claim stores the tenant eight-hex UUID, and
  `auth_sessions.tenant_id` is `VARCHAR(64)`. That is existing Platform behavior, not the pattern for
  new foreign keys.

## Regression tests

- Platform unit tests for issuance, claim tampering, tenant substitution, revocation, and audience
  separation.
- Tenant-boundary E2E: customer A cannot read customer B in the same tenant or any other tenant.
- Ecommerce tests assert every portal route denies without a principal and requires the scoped
  permission.
- Existing EC-T01 staff/journey tests remain green.

## Owner decision still required

1. Is self-registration allowed, or invitation/admin-created only?
2. Is a customer bound to one Core contact, or may one login represent multiple companies?
3. Does a vendor principal require a verified company relationship before offers/settlement?
4. Is a portal login tenant-scoped (recommended, matching current tenant login), or must one account
   work across tenants? A cross-tenant account needs the master binding described above and must still
   keep contact/company data tenant-local.
5. May one email hold both a customer and a vendor principal in the same tenant? The proposed keys
   allow it; deny it explicitly if the business requires one identity per email.

Recommended default: invitation/admin-created, one principal per Core contact per tenant, vendor
membership requires an active company relationship, and a portal login is tenant-scoped. These are
reversible; parallel Ecommerce identity is not.
