# Marketing Working Rules

## Apply this guidance

Read the repository agent guide and governance rules before changing this component.
Read [README](../README.md), [PLAN](PLAN.md), and [TASK](TASK.md) before planning or implementing Marketing.
Read affected app documents before modifying CRM, Sites, Mail, Chat, Core, Billing, Platform, or Zetro.
This document guides development. It does not grant runtime permissions, provider access, or deployment approval.

Current authorization permits Phase 1 implementation and verification locally.
Do not deploy, commit, push, or change versions until the user requests it.
Preserve unrelated and concurrent working-tree changes.

## Product boundaries

- Build one tenant Marketing application with the same dashboard shape for every client.
- Keep each client's business records in its own tenant database.
- Keep company and brand permissions inside the tenant boundary.
- Exclude TikTok.
- Include email campaigns as essential delivery scope.
- Reserve all-client management for a separate future Super Admin app.
- Keep acquisition, campaign execution, raw submissions, nurturing, and attribution in Marketing.
- Keep canonical sales Leads, qualification, enquiries, sales assignments, and follow-up in CRM.
- Keep contact identity in Core, public pages in Sites, email transport in Mail, and existing Telegram transport in Chat.
- Follow the reconciled ownership: Marketing Campaign/promotional consent, CRM service-contact restrictions, and Mail delivery-safety suppression.
- Preserve existing Sites, TConnect, Sportsclub, and Ecommerce business records. Never create duplicate owners.

## Tenant and connector rules

Use only server-validated tenant registry context for database, file, queue, and connector routing.
Never trust a browser tenant header, callback tenant parameter, public identifier, or account ID as proof of authorization.
Verify company, brand, record, and connector access for every read and mutation.
Partition caches, locks, idempotency keys, jobs, files, exports, and live updates by trusted context.
Workers must restore tenant context and recheck current activation, grants, consent, suppression, approval, and connection state.

Bind OAuth state to tenant, session, actor, provider, and an approved return destination.
Reject expired/replayed state and validate account ownership before saving a grant.
Encrypt tenant credentials server-side. Keep shared developer secrets in protected deployment configuration.
Never collect provider passwords or session cookies. Never expose refresh tokens in the browser or audit logs.
Route webhooks through trusted account/subscription mappings and verify provider authenticity before processing.
Reject ambiguous mappings and stale subscriptions. Do not infer a tenant from an untrusted payload.
Do not attach the same external account to another tenant without an explicit, audited transfer contract.

Disconnect must stop unsent local work and revoke only the affected grant or subscription.
Do not revoke a shared developer application or another client's access while disconnecting one tenant.
Public media, unsubscribe, preview, and tracking links require separate limited-purpose access rules.
No future support feature may bypass current tenant checks.

## App and module ownership

Use concrete module-owned migrations, repositories, services, routes, types, seeds, forms, lists, hooks, and workspaces.
Add executable event/worker/sync roles only when needed. Do not create placeholder role files.
Use fixed public contracts, approved events, or injected dependencies for cross-app operations.
Do not import another app's private repository, service, form, hooks, schema, or internal database tables.
Keep Platform composition free of Marketing business CRUD.
Keep Mail provider adapters and credentials in Mail. Marketing references permitted Mail sender settings.
Existing Chat Telegram uses account sessions and polling. Do not describe it as a ready Bot API connector.
Chat owns the future bot adapter and its webhook. Marketing must not duplicate account credentials or provider event consumers.
Use governance public `uuid` identifiers and validate authorization independently of identifier secrecy.

## UI and action rules

Read `assist/documentation/design-system-helper.md` before UI work.
Use CRM Enquiry list, Show, and upsert as the visual and interaction reference.
Marketing list and upsert modes must render separate page views. Never render a list behind an upsert form.
Place Filters and Columns in the search toolbar. Preserve filter and column state in the page URL.
Use `@codexsun/ui` primitives with the same density, spacing, typography, tones, buttons, forms, and activity rhythm.
Customize domain fields, channel previews, tabs, and useful calendar behavior inside Marketing.
Do not import private CRM UI or create a generic metadata-driven business workspace.
Implement the relevant action matrix in PLAN with backend permissions and lifecycle checks.
Provide loading, empty, validation, API error, confirmation, pending, and success states.
Stop button/menu propagation inside clickable rows. Preserve direct links and browser-back behavior.
Recheck every selected record during bulk actions and show partial results.
Do not render nonfunctional buttons or fake connection, delivery, publication, or report data.

## Campaign, lead, and delivery rules

Persist submissions and handoff intent before requesting CRM work.
Use stable retry identities and preserve original source references.
Review ambiguous matches. A phone number or email address alone must not merge customer identities.
Keep provider test data outside production metrics.
Bind approval to the exact revision, sender/account, audience policy, schedule, and limits.
Invalidate approval after material changes.
Reconcile uncertain provider outcomes before retrying non-idempotent publishing or sending.
Keep draft, queued, provider-accepted, published/delivered, failed, and manual-completed evidence distinct.

Email requires verified sender setup, consent, unsubscribe, bounce/complaint handling, and execution-time suppression.
SMTP acceptance does not prove inbox delivery. Opens and clicks do not prove human engagement.
Imports do not imply consent. Do not add purchased/scraped list acquisition.
Pause/cancel affects unsent work and cannot recall provider-accepted email.
Stop relevant nurturing after reply, opt-out, conversion, complaint, suspension, or human takeover.
AI actions must respect Zetro grants and required confirmation. Prompts cannot authorize business actions.

## Provider validation

Use current official provider documentation before implementing or changing a connector.
Track publishing, comments, messaging, lead retrieval, analytics, and advertising as separate capabilities.
Record actual approval, account type, scopes, format limits, quotas, costs, and fallback behavior.
Do not assume access from a connection status or developer test token.
Use supported native publishing tasks or authorized imports when API access is unavailable.
Do not use scraping, login bots, cookie capture, or arbitrary mass direct messaging as substitutes.

## Verification and reporting

For a small change, inspect the affected code and use at most one focused check when useful.
Inspection can suffice for a trivial edit. Add checks when the change and its risks require them.
For affected tenant, authorization, OAuth, webhook, queue, consent, or approval behavior, test relevant negative paths.
Run broad audits, full builds, browser acceptance, and provider pilots when requested or required by the change.
Record evidence for the work performed and report material verification limits.
Do not claim production, browser, persistence, provider, or delivery verification from compilation or documentation checks.
Do not bump versions, publish, send campaigns, connect client accounts, or deploy as part of a documentation-only task.

## Promotional evidence and current eligibility

Email is the first supported promotional eligibility channel. Reject unsupported channels and purposes.
Consent evidence is append-only. Preserve withdrawals and require later evidence for re-consent.
Missing authorities, grants, activation, or migrations must block eligibility.
Check every matching Core identity through its public lookup. Do not merge recipients or bypass existing CRM preferences.
Never clear Mail complaint, bounce, or policy suppression from Marketing.
An eligibility result is an assessment at check time. It cannot authorize a future queued send by itself.
Do not add promotional dispatch to existing SMTP or system-send paths without the planned execution contract.
